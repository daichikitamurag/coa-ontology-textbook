第 0 章

この本の読み方

先に、この本が何をしようとしているかを説明します。ここを読めば、自分に必要な章だけ拾う判断もできます。

この本が答える問い

技術用語を並べた解説は世の中にたくさんあります。しかし読んでも「で、結局どれを使うと何が嬉しいのか」が残らないことが多い。原因は、道具の説明が、解こうとしている問題から切り離されていることだと思います。

そこでこの本は、最初にたった 1 つの実務的な失敗を提示します。そして各章で道具を 1 つずつ導入し、その道具がこの失敗のどの部分を解くのかを毎回確認します。最終章まで来ると、次の問いに自分の言葉で答えられるようになります。

  • オントロジーとは何で、DB スキーマと何が違うのか
  • Turtle / RDFS / OWL / SHACL / SPARQL は、それぞれ何を担当しているのか
  • 「推論する」とは具体的にどういう計算なのか
  • OWL と SHACL は似ているのに、なぜ両方あるのか
  • AWS COA のような製品は、このうち何を実装して何を実装していないのか

この本を貫く 1 つの例

全章を通じて、次の 1 つの依頼を扱います。本書ではこれを題材と呼びます。

題材

この本に出てくる 3 人の登場人物

定義 — この本で「機械」と呼ぶもの

LLM ではないソフトウェア、つまり決まった手続きで動くプログラム群を指します。具体的には次の 5 つで、すべて本書に登場します。

ここで用語を 1 つ片付けておきます。この 2 つは混同されがちですが、はっきり違います。AI Agent とは「LLM と機械を組み合わせたもの」です。

第 2 章で書く SQL は、文法的に正しく、実行も通り、もっともらしい数字を返します。間違っていることを示す手がかりが、どこにも出ません。だから問いはこうなります —この間違いは、誰が見つけるのか。

候補見つけられるか理由
人間ほぼ無理全件は追えない。そもそも「どちらの数字が正しいか」は社内の定義を知らないと判断できない
LLMできない自分が推測で埋めた箇所を「推測した」と認識できない。同じ質問でも違う答えを返しうる
機械できるただし文章は読めない。ルールが機械の読める形で書かれていなければ、検証そのものが成立しない

これが本書の全体像です。間違いを減らすために、機械に検証させる。機械に検証させるために、定義を機械が読めるデータとして書く。順番はこれだけです。

では Agent はどこで関わるのか。書き込むかどうかではありません。出力が人間の目を通らずに、そのまま次の処理へ進むからです。人が画面を見て「あれ?」と思う機会が、構造として存在しません。だから検証はあらかじめ機械側に置いておくしかない。本書で SHACL や推論器を扱うのは、そのためです。

補足: 「Agent = 必ず書き込む」ではありません。第 12 章で見る AWS COA は Read-only です。それでも検証の必要性は変わりません。止める場所が「書き込みの直前」から「答えを返す直前」に移るだけです。

1.3 この一文に埋まっている、社内にしか無い定義

依頼の中に、データベースを見ても絶対に分からないものが 4 つあります。

言葉DB から分かることDB から分からないこと
優良顧客member_rank と total_purchase という列があることだけmember_rank 列で判定するのか、金額で判定するのか。この会社の答えは「累計購入額 50,000 円以上」で、member_rank 列は営業部の手運用なのでズレている
アクティブ顧客 last_order_at と churned_at という列があることだけ 「直近 何日」なのか。解約者を除くのか。この会社の答えは「直近 90 日以内に購入、かつ未解約」だが、どこにも書かれていない
売上 amount / tax / refunds.amount / status という列があることだけ 税を引くのか。返金を引くのか。pending を含めるのか。この会社の答えは「税抜・返金差引後・confirmed のみ」
先月 order_date がある 暦月か会計月か。この会社は暦月なので、ここは実害が少ない

ここで大事なのは、これらが「書き忘れ」ではないということです。DDL は格納構造を書くための言語であって、業務概念を書くための言語ではありません。書く場所が用意されていないのです。

2.3 何が起きたのか — 金額よりも深刻なこと

2 つの数字を並べます。

図 2-1同じ依頼、2 つの答え

金額が近いほど発見されにくい。「もっともらしい間違い」が一番危ない

どちらの SQL もエラーを出しません。つまり間違いに気づく手がかりが、どこにも現れません。そして依頼は「レポートにして」でした。この数字はレポートになり、会議資料になり、他システムに連携されます。手がかりが無いまま、間違いが下流に広がっていきます。

2.4 「プロンプトに書けばいい」では続かない理由

ここで多くの人が思いつく解決策があります。AI に SQL を書かせるなら、定義をプロンプトに書いておけばいい。実際、小さいうちは動きます。しかし 4 つの理由で続きません。

理由中身
① 書き切れないアクティブ顧客・売上・解約・与信・稼働率… 全部門分の定義を文章で書き溜めるのは現実的ではない
② 長いほど弱くなる定義を足すほどプロンプトが伸び、真ん中の情報は読み飛ばされる。ルールを増やすと精度が下がるという逆転が起きる
③ 変更が掛け算で効く「90 日を 60 日に変える」と決まったとき、Agent の数 × 業務の数だけプロンプトを直す必要がある
④ 機械が再利用できない文章なので、人間と LLM しか読めない。第 0 章で定義した「機械」(推論器・SHACL 検証器・クエリエンジン) は文章を計算に使えないため、ルールが適用されたかを機械的に検証できない

④ が本質です。プロンプトに書いた定義は「LLM が読んで解釈する対象」になります。つまり適用されるかどうかが確率的になり、しかも「適用されたか」を後から機械的に確かめられません。

この本が目指す地点

必要なのは、定義を「文章」ではなく「機械が計算に使えるデータ」として書くことです。そうすれば、同じ 1 つの定義を LLM も・推論器も・検証器も・SQL 生成器も共通に参照できます。
次の章から、そのための記法を学びます。

第 2 章のまとめ
  • 定義を知らずに書いた SQL は 89,000 円、正しい SQL は 84,500 円。どちらもエラーなく実行される
  • 本当に怖いのは金額差ではなく、同じ言葉で違う人を数えていたこと (高橋 vs 鈴木)
  • プロンプトに定義を書く方法は、機械が再利用できないという点で行き止まり
  • 目標は「定義を、機械が計算に使えるデータとして書く」こと
第 3 章

トリプル — 世界を 3 語で書く

意味を機械に書くための、たった 1 つの部品を学びます。これだけ理解すれば、以降の章はすべてこの部品の組み合わせです。

3.1 表の 1 行を、文に分解する

表 1-1 の佐藤花子さんの行を見てください。

customer_idnamemember_ranktotal_purchaselast_order_atchurned_at
C001佐藤 花子VIP82,0002026-07-28(null)

この 1 行を、日本語の文にばらしてみます。

  • C001 の 名前は 佐藤 花子 である
  • C001 の 会員ランクは VIP である
  • C001 の 累計購入額は 82000 である
  • C001 の 最終注文日は 2026-07-28 である

どの文も 「誰が」「何の」「何である」 の 3 語でできています。これがトリプル (triple)です。RDF の世界では、すべてをこの 3 語の文で書きます。

定義 — トリプル

主語 (Subject) — 述語 (Predicate) — 目的語 (Object) の 3 つ組で表す、1 つの事実。
英語の語順と同じで、最後にピリオド . を打って 1 文が終わります。

:C001  :会員ランク  "VIP" .
└主語┘  └─述語─┘  └目的語┘

3.2 なぜ「行」ではなく「トリプル」なのか

RDB (Relational Database) は「行」が最小単位です。1 行が複数の列を抱えています。RDF (Resource Description Framework) は1 事実 = 1 トリプル。行をバラバラに分解した粒度です。名前が 1 字違いで紛らわしいので、ここで並べておきます。

面倒に見えますが、決定的な利点があります。列を増やすのに、テーブル定義を変える必要がありません。「佐藤さんは営業部の山田さんが担当している」という事実を足したいとき、RDB なら ALTER TABLE が必要です。RDF なら、トリプルを 1 本足すだけです。

リスト 3-1事実を足すのは、行を足すだけ

# もともとあった事実
:C001 :会員ランク "VIP" .
:C001 :累計購入額 82000 .

# 後から足したい事実 → テーブル定義を変えずに 1 行足すだけ
:C001 :担当営業 :S07 .
:C001 :優先サポート対象 true .

3.3 なぜ文字列ではなく URI なのか

ここが最初のつまずきポイントです。RDF では主語と述語に、文字列ではなく URI (URL のようなもの) を使います。:C001 や :会員ランク は略記で、本当は次のような長い識別子です。

リスト 3-2略記の正体

# 略記
:C001 :会員ランク "VIP" .

# 本当の姿
<http://example.com/ec#C001>
  <http://example.com/ec#会員ランク>
  "VIP" .

なぜこんな面倒なことをするのか。理由は 1 つです。同じ名前の別物を、機械が確実に区別できるようにするためです。

ただし正直に言うと、URI だけでは第 2 章の事故は防げません。あの事故は「アクティブ顧客」の定義が 2 通りに解釈されたから起きたので、識別子を一意にしただけでは解決しません。

URI が用意するのは「定義を貼り付ける場所」です。ec:アクティブ顧客 という一意な URI があれば、そこに「直近 90 日」「未解約」という定義をぶら下げられます。貼る場所を作るのが第 3 章、実際に貼るのが第 5〜6 章という分担です。

文字列で管理するとURI で管理すると
「顧客」が営業部と経理部で違うものを指すsales#顧客 と fin#顧客 は別の URI なので機械が別物と分かる
他社のデータと突き合わせると名前が衝突するURI にドメインが入るので衝突しない
業界標準の用語集と繋げられない医療の SNOMED CT などが公開している URI をそのまま参照できる

3.4 トリプルを並べると、グラフになる

トリプルは 3 語の文ですが、たくさん並べると点と矢印の網になります。主語と目的語が点、述語が矢印です。

図 3-1表の 2 行が、グラフになる

RDB の「JOIN」に相当するものが、ここでは単に矢印を 1 本辿ることになっている

この図の :注文した について

ここでは顧客から辿る話をしているので、顧客 → 注文の向きに :注文した と書いています。ただし第 4 章以降で使うデータは逆向きで、ec:O101 ec:注文者 ec:C001 .（注文 → 顧客）と書きます。

同じ関係を、どちら側から見るかの違いです。どちらか一方を書けば、もう一方は導けます。その書き方は第 6 章の owl:inverseOf、辿り方は第 7 章の ^ で出てきます。

ここに注目してください。:C001 → :注文した → :O101 → :金額 → 44000 という経路は、SQL なら customers JOIN orders が必要でした。グラフでは矢印を 2 本辿るだけです。第 7 章の SPARQL で、この違いが効いてきます。

第 3 章のまとめ
  • トリプル = 主語・述語・目的語の 3 語で書く 1 つの事実
  • RDB は「行」が最小単位、RDF は「1 事実」が最小単位。だから列の追加が定義変更にならない
  • 主語と述語に URI を使う理由は「同名の別物を機械が区別できるようにする」ため
  • トリプルを並べるとグラフになり、JOIN が「矢印を辿る」に変わる
第 4 章

Turtle — トリプルを書く記法

トリプルをファイルに書くための書式を学びます。覚えることは 5 つだけです。この章を終えると、第 1 章の表を全部 Turtle で書けるようになります。

最初に混乱を潰しておく

Turtle と「オントロジー」は並列の概念ではありません。よくある混乱なので先に整理します。

Turtleオントロジー
正体トリプルを書く記法 (文法)意味の設計 (中身)
例えるとJSON / YAML と同じレイヤーDB スキーマ設計・クラス図と同じレイヤー
代替物RDF/XML, JSON-LD, N-Triples
(同じ内容を別の書式で書ける)		代替物ではなく、Turtle で書かれる中身そのもの

正しい言い方は 「オントロジーを Turtle 形式で書く」です。「Turtle とオントロジーどっちを使う?」という問いは成立しません。

4.1 覚えるべき記法は 5 つ

先に 1 つだけ、記法ではなく句読点の話をします。Turtle では . (ピリオド) が「トリプル 1 本の終わり」を表します。英語の文末のピリオドと同じ役目です。

リスト 4-0ピリオドが 1 本の区切り

ec:C001 ec:名前 "佐藤 花子" .      # これで 1 本 (1 つの事実)
ec:C001 ec:会員ランク "VIP" .    # これで 2 本目

あとは改行や空白は自由です。区切りはピリオドだけが決めます。では本題の 5 つに入ります。

① @prefix — 長い URI に短い名前を付ける

リスト 4-1prefix 宣言

@prefix ec: <http://example.com/ec#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .  # 型を書くための語彙
@prefix owl: <http://www.w3.org/2002/07/owl#> .     # クラスを宣言する語彙。詳しくは第 6 章

# これで ec:C001 と書けば <http://example.com/ec#C001> の意味になる
ec:C001 ec:名前 "佐藤 花子" .

② a — 「〜の一種である」を表す 1 文字

a は rdf:type の略記で、Turtle 独自の糖衣構文です。「これは〇〇という種類のものだ」を意味します。

リスト 4-2a の使い方 — クラス宣言もインスタンス化も同じ記法

# 「顧客」という種類(クラス)を定義する
ec:顧客 a owl:Class .

# C001 は「顧客」の一種である と宣言する
ec:C001 a ec:顧客 .

SQL で言えば、上が CREATE TABLE、下が INSERT に相当します。RDF では両方を同じ a で書きます。DDL と DML の区別すら要りません。

③ ; — 主語を省略して続けて書く (. との使い分け)

リスト 4-3セミコロンで主語を省略する

# 冗長な書き方
ec:C001 ec:名前 "佐藤 花子" .
ec:C001 ec:会員ランク "VIP" .
ec:C001 ec:累計購入額 82000 .

# セミコロンでまとめる (意味は全く同じ)
ec:C001 ec:名前 "佐藤 花子" ;
        ec:会員ランク "VIP" ;
        ec:累計購入額 82000 .

違いは 1 つだけです。; は「主語はさっきと同じ。次の述語へ」、. は「ここで 1 本おわり」。だから ; で繋いだ最後には必ず . が来ます。

④ 型付きリテラル — 値の種類を明示する

目的語が「値」のとき、その型を ^^ で指定できます。この型指定が第 6 章と第 9 章で罠になるので、いま覚えてください。

リスト 4-4型付きリテラル

ec:C001
  ec:名前       "佐藤 花子"                        # 型なし = 文字列
  ; ec:累計購入額 "82000"^^xsd:decimal          # 10進数 (正確な数)
  ; ec:最終注文日 "2026-07-28"^^xsd:date        # 日付
  ; ec:優先対象   "true"^^xsd:boolean         # 真偽値
  .

⑤ [ ] — 名前のない「もの」を作る

URI を付ける必要がない中間的な存在を書くときに使います。空白ノード (blank node)と呼びます。いまは「こういう書き方がある」だけ覚えて、第 6 章で本格的に使います。

リスト 4-5空白ノード

# 「金額 5500 円の返金がある」— 返金そのものに ID を振らない書き方
ec:O101 ec:返金 [ ec:金額 5500 ] .

4.3 TBox と ABox — 定義とデータを区別する

次の 2 行を見比べてください。形は同じですが、性質がまったく違います。

リスト 4-7定義とデータ

ec:顧客 a owl:Class .        # ← 「顧客というクラスが存在する」= 定義
ec:C001 a ec:顧客 .         # ← 「C001 は顧客である」    = データ
定義 — TBox と ABox

TBox (Terminological Box) = クラスやプロパティの定義。「世界にはどんな種類のものがあるか」。
ABox (Assertional Box) = 個々の事実データ。「実際にどんなものがあるか」。

狭い意味で「オントロジー」と呼ばれるのは TBox のほうです。そして第 9 章に出てくる推論器は、TBox と ABox の両方を受け取って、新しい ABox を導き出します。この関係が推論を理解する鍵になります。

重要 — 実務では ABox を手で書きません

リスト 4-6 で 5 人分のデータを Turtle で書いたのは、記法を学ぶためです。実務でこれをやると、元の DB と Turtle の二重管理が始まってしまいます。

実際の製品 (AWS の COA — Context Ontology Accelerator など) が採る方式では、格納されるのは TBox (定義) と対応表だけです。

Triple Store (Neptune 等) に入るもの入らないもの
クラス定義 ec:顧客 a owl:Class佐藤さんの実データ
プロパティ定義 domain / range / label注文 5 件の実データ
階層 rdfs:subClassOf返金の実データ
RDB との対応表 (第 11 章の R2RML)— つまり ABox 全体

では ABox はどこへ行ったのか。元の RDB に居続けます。そして SPARQL を投げた瞬間に SQL へ翻訳されて取りに行きます。「保存せずに、あるように見せる」のです。

この方式を VKG (Virtual Knowledge Graph) と呼びます。第 10〜11 章で詳しく扱いますので、いまは「手で書いた Turtle は学習用で、実務では自動生成される」と覚えておいてください。

第 4 章のまとめ
  • Turtle は記法、オントロジーは中身。「オントロジーを Turtle で書く」が正しい言い方
  • 行末の . が 1 トリプルの終わり。覚える記法は 5 つ: @prefix / a / ; / ^^ 型指定 / [ ] 空白ノード
  • クラス宣言もインスタンス化も同じ a で書ける（DDL と DML の区別が要らない）
  • TBox = 定義、ABox = データ。推論器は両方を食べて新しい ABox を出す
  • ただし、ここまではまだ表の写しにすぎない。意味は次章から
第 5 章

RDFS — 語彙に意味を与える

Turtle で書けるようになりましたが、まだ「表の写し」でした。この章で ec:会員ランク という記号に人間と機械が読める意味を与えます。使う語彙は 5 つだけです。

5.1 rdfs:label — 記号に人間の言葉を与える

第 2 章で新人が外した原因を、もう一度並べます。① 「直近 90 日」という基準を知らなかった ② churned_at という列の存在に気づかなかった ③ 「売上」が税抜・返金差引後だと知らなかった。

3 つとも「列の名前を見ただけでは分からない」ことです。RDFS の rdfs:label と rdfs:comment は、この情報を列そのものに貼り付けるための語彙です。

リスト 5-1ラベルを付ける

@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ec:会員ランク
    rdfs:label   "会員ランク"@ja ;
    rdfs:label   "Membership Rank"@en ;
    rdfs:comment "VIP または Regular。営業部が四半期ごとに手動更新している"@ja .

上は第 6 章で使う ec:会員ランク の例です。では、第 2 章の事故に直接効く書き方を見てください。

リスト 5-1b事故の原因になった 2 つの列に注意書きを貼る

ec:最終注文日
    rdfs:label   "最終注文日"@ja ;
    rdfs:comment "アクティブ顧客の判定に使う。基準は直近 90 日 (2026-04 の営業会議で決定)"@ja .

ec:解約日
    rdfs:label   "解約日"@ja ;
    rdfs:comment "値があれば解約済み。アクティブ顧客の判定では必ず除外する"@ja .

もしこの 2 行が書かれていれば、第 2 章の新人は「30 日くらいかな」と推測する必要がなく、churned_at を見落とすこともありませんでした。ラベルは名前を与えるだけですが、rdfs:comment は「この列をどう扱うべきか」を運べます。

@ja / @en は言語タグです。同じ概念に複数言語のラベルを付けられるので、「取引先」と「customer」が同じ URI にぶら下がります。

ラベルとコメントを読んで使うのは、誰か

rdfs:label と rdfs:comment は、人間と LLM にとってはこの章でいちばん意味の濃い部分です。第 2 章の事故を防ぐのは、まさにこの 2 つでした。

ところが推論器にとっては、この 2 つは意味を持ちません。第 9 章の HermiT はラベルを一切見ませんし、第 8 章の SHACL 検証器も同じです。「意味が無い」のではなく、「機械が計算に使える形になっていない」ということです。中身は日本語の文章なので、機械には文字列でしかありません (第 2 章 §2.4 の ④)。

誰が使えるか何ができるか
人間使える読んで理解する。後任者への申し送りになる
LLM使える表記揺れを吸収できる。「お取引先様」でも ec:顧客 に結びつけられる
機械ほぼ使えないSPARQL で rdfs:label "取引先"@ja の完全一致検索はできる。しかし「お取引先様」は引けず、推論器は一切使わない

では、この 2 つは何のために置かれているのか。言葉で説明すると長くなるので、図で見ます。

図 5-1ラベルとコメントは、人間の言葉と機械の世界をつなぐ足場になる

溝は 2 つある。語の対応を埋めるのが rdfs:label、判定基準を埋めるのが rdfs:comment。第 2 章の新人が外したのは後者だった

そして rdfs:comment が地味に重要です。ここに「営業部が手動更新している」と書いておけば、この列を信用しすぎてはいけないことが、後任者にも、そして LLM にも伝わります。第 6 章でこれが効いてきます。

5.2 rdfs:domain / rdfs:range — プロパティの両端を決める

一言で言えば、プロパティに 2 つのことを宣言します。どのクラスに付くプロパティなのか (rdfs:domain) と、その値はどのクラス、または型なのか (rdfs:range)。それだけです。

まず、素直なイメージから

プログラムのクラス定義とほぼ同じ形だと思って構いません。

// もし OO 言語のクラス定義なら
class 注文 {
    注文者: 顧客      // 値は「顧客」型
    金額:   decimal
}

RDFS ではプロパティを主語にして、両端を別々に書きます。似ていますが、所有関係が逆です — クラスがプロパティを抱えるのではなく、プロパティの側が「自分はどのクラスに付くか」を指しています。

ec:注文者

5.4 5 つの語彙のまとめ

語彙種類主に使うのは解決する問題
rdfs:label注釈人間 / LLM用語の不一致 — 「取引先」と customer を同じ URI に結びつける
rdfs:comment注釈人間 / LLM第 2 章の事故そのもの — 「基準は 90 日」「解約者は除外」を列に残せる
rdfs:domain公理推論器 / LLM / VKGJOIN 問題 — 参照関係が明示される
rdfs:range公理推論器 / LLM / VKG同上 + 型の明示

この 5 つは、性質の違う 2 群に分かれている

同じ RDFS の語彙として並んでいますが、中身は 2 種類あります。ここを混ぜて覚えると、後の章で誰が何をしているのか分からなくなります。

注釈 (label / comment) — 人間と LLM に向けた言葉。役割は人間の言葉と URI の間を橋渡しすることで、実際にその橋を渡るのは人間と LLM です。推論器はこれを読みませんが、意味が薄いわけではありません。むしろ第 2 章の事故を防ぐのはこちらです。ただし機械が計算に使える形ではないので、効かせるには LLM に渡す必要があります。第 12 章で COA がこれをプロンプトに入れるのは、そのためです。

公理 (domain / range / subClassOf) — 機械が計算に使える形の意味。推論器が計算に使い、書いていない事実を導きます (第 9 章)。ec:C001 a ec:優良顧客 から ec:C001 a ec:顧客 が出てくるのは、LLM が推測したのではなく機械が導いた結果です。

つまり第 5 章は、「人間の自然言語と機械の形を LLM が対応づけるための橋」と「機械が推論するための土台」を、同時に用意している章です。次章の OWL は後者だけを深めていきます。

実務での重み — なぜ label は「必ず書かれる」のか

第 1 章で「DDL の COMMENT は実務でほとんど書かれない」と述べました。RDFS の rdfs:label は事情が違います。書かないと後続の道具が動かないのです。オントロジーの編集ツールは入力を促し、SPARQL を書く人はラベルを頼りにし、LLM に渡すプロンプトはラベルから組み立てられます。
「同じことが書ける」より「実際に書かれるか」が生態系の差になります。

第 5 章のまとめ
  • rdfs:label で記号に人間の言葉を与える → 用語の不一致が解ける
  • rdfs:comment で「この列をどう扱うか」を残せる → 第 2 章の「90 日」と「解約者を除外」が書ける場所ができた
  • rdfs:domain / rdfs:range で述語の両端を宣言する → JOIN 問題が解ける
  • rdfs:subClassOf で階層を作る → 推論の土台になる
  • 5 つは 2 群に分かれる — label/comment は注釈で人間と LLM が使う。domain/range/subClassOf は公理で推論器が計算に使う
  • しかし 「アクティブ顧客とは何か」はまだ書けていない。それには OWL が必要 (次章)
第 6 章

OWL — 型とルールを定義する

本書の山場です。ここで初めて「条件を満たすものは、この型である」と書けるようになります。SQL にはこの構文がありません。そして OWL の限界も、この章で正直に確認します。

6.1 SQL では「新しい型」を作れない

「累計購入額 5 万円以上の顧客は優良顧客とする」というルールを SQL で書いてみます。

リスト 6-1SQL でやろうとすると、VIEW にしかならない

CREATE VIEW good_customers AS
  SELECT * FROM customers WHERE total_purchase >= 50000;

SQL に「新しい区分を作る」文法はありません。無理に表現しようとすると、上のように VIEW になります。

しかし View は「型」ではなく「その場の検索結果」でしかありません。佐藤さんは「優良顧客」という型になるのではなく、View の結果に現れるだけです。

だから他の場所から「優良顧客」を名前で指せません。たとえば優良顧客だけの割引表を作ろうとしても、SQL の REFERENCES が指せるのはテーブルだけで、View は指せません。顧客テーブル全体を参照するしかなく、「優良顧客だけ」を守らせたければ total_purchase >= 50000 をもう一度どこかに書くことになります。条件が 2 箇所に増えます。

欲しいのは 「優良顧客」という名前で参照できる型です。条件は 1 箇所に書き、割引表も制約も検査もその名前を指すだけで済む形。それを書けるのが、次節の OWL です。

6.2 OWL なら「型」として書ける

OWL の owl:equivalentClass は「この条件を満たすものは、この型と同じである」と宣言します。

リスト 6-2優良顧客を「型」として定義する

@prefix owl: <http://www.w3.org/2002/07/owl#> .

ec:優良顧客 a owl:Class ;
    rdfs:label "優良顧客"@ja ;
    rdfs:comment "累計購入額 5 万円以上の顧客。2026-04 の営業会議で決定"@ja ;
    owl:equivalentClass [
        a owl:Class ;
        owl:intersectionOf (
            ec:顧客                              # ① 顧客であって
            [ a owl:Restriction ;                  # ② かつ
              owl:onProperty ec:累計購入額 ;      # 見るのは累計購入額
              owl:someValuesFrom                  # その値が…
                  [ a rdfs:Datatype ;             # 「こういう数値」という型をその場で作る
                    owl:onDatatype xsd:decimal ;  # 土台は decimal
                    owl:withRestrictions          # そこに条件を足す
                        ( [ xsd:minInclusive "50000"^^xsd:decimal ] )  # 50000 以上
                  ] ]
        ) ] .

記号が多くて驚くかもしれませんが、読み方は単純です。「優良顧客 = 顧客であり、かつ 累計購入額が 50000 以上のもの」と書いてあるだけです。第 4 章で覚えた [ ] (空白ノード) が、括弧の入れ子として使われています。

6.4 OWL の担当範囲 — 書けるもの、書けないもの

題材の依頼には、定義が必要な言葉が 2 つ入っていました。「優良顧客」は前節で書けました。では「アクティブ顧客」はどうでしょうか。

まず分解します。この会社の定義は ① 直近 90 日以内に購入 ＋ ② 解約していない の 2 つでした。② は OWL で書けます。「解約日というプロパティを 1 つも持たない」を基数制約で表現します。

リスト 6-3書ける部分だけ書く — 未解約の表現

ec:継続顧客 a owl:Class ;
    rdfs:label "継続顧客 (解約していない顧客)"@ja ;
    owl:equivalentClass [
        a owl:Class ;
        owl:intersectionOf (
            ec:顧客
            [ a owl:Restriction ;
              owl:onProperty ec:解約日 ;
              owl:maxCardinality "0"^^xsd:nonNegativeInteger ]
              # ↑「解約日を 0 個持つ」= 解約していない
        ) ] .

これを 5 人に当てはめると、高橋さん (C004) だけが継続顧客ではないと判定されます。第 2 章で新人が見落とした条件が、これで機械可読になりました。

残ったのは ① 直近 90 日以内に購入 です。こちらは OWL では書けません。理由は 3 つ重なっています。

OWL が「直近 90 日」を書けない 3 つの理由

① 「今日」が存在しない。OWL に NOW() や CURRENT_DATE にあたるものはありません。「今日から数えて 90 日」の起点が取れません。

② 条件に書けるのは固定値との比較だけ。前節の xsd:minInclusive "50000" のように、動かない値とだけ比べられます。「今日 − 90 日」は日ごとに動くので書けません。

③ 値と値を比べられない。これは意外に思われるところですが、OWL 2 では同じ個体が持つ 2 つのプロパティを比較することすらできません。「注文日 < 出荷日」も書けません。

そしてこれは「機能が足りない」というより設計思想の違いです。OWL のクラスは「いつ聞いても同じ集合」を表すものとして作られています。一方「アクティブ顧客」は毎日中身が変わります。昨日のアクティブ顧客と今日のアクティブ顧客は別の集合です。そういうものを型として定義するのは、そもそも OWL の役目ではありません。

だから題材の 2 語は、担当が分かれます。

言葉担当なぜ
優良顧客OWL「累計 50,000 円以上」は固定値との比較。いつ聞いても同じ集合になる (§6.2)
継続顧客
＝ 未解約		OWL「解約日を 0 個持つ」は個数の条件。時間も比較も要らない (リスト 6-3)
アクティブ顧客OWL では不可「今日から 90 日」は毎日動く条件。SPARQL / SHACL / バッチの担当 (次の表)
「アクティブ顧客」をどう扱うか — 実務の答え

時間に依存する条件は、OWL の外で扱います。実務では次の 3 つのどれかを選びます。

方法中身
① SPARQL で書く問い合わせ側で FILTER として書く。最も現実的 (第 7 章)
② SHACL で書く「アクティブ顧客のはずなのに条件を満たさない」の検査として書く (第 8 章)
③ 毎日再計算して書き込むバッチで基準日を計算し、ec:C001 a ec:アクティブ顧客 をデータとして書き込む

重要なのは、どの方法を選んでも「90 日」という数字と「未解約」という条件が 1 箇所に集約されることです。プロンプトに散らばっていた状態からは前進しています。

6.6 罠 — xsd:decimal と xsd:double は別世界

実際に踏んだ罠

リスト 6-2 で xsd:decimal と書きました。もしデータ側が xsd:double で入っていたら、このルールは 1 件もヒットしません。しかもエラーが出ません。

OWL 2 の仕様では、数値型が 2 つの独立した系統に分かれています。

xsd:decimal 系  # 正確な 10 進数
  ├─ xsd:integer
  └─ xsd:long, xsd:int, xsd:short ...

xsd:double 系   # IEEE 754 浮動小数点 — 別系統!
xsd:float  系   # IEEE 754 浮動小数点 — 別系統!

この 2 つの値の集合は互いに素 (disjoint) と定義されています。つまり「decimal で 50000 以上」という条件に、double の 82000 は論理的に該当しません。SQL の暗黙型変換に慣れていると、まず気づけません。

対策: データ側の型を確認してから公理を書く。自動生成されたオントロジーは SQL の DOUBLE 列を xsd:double にすることが多いので、公理側を xsd:double に合わせるのが実務的です。

第 6 章のまとめ
  • owl:equivalentClass で「条件を満たすものはこの型である」と書ける。SQL にこの構文は無い
  • 優良顧客ルールを 5 人に当てると 4 名。しかし member_rank 列は 2 名。この 2 名のズレを機械的に発見できることが最初の価値
  • 第 2 章で新人が条件に入れられなかった「優良顧客」が、名前を持つ型になった。member_rank 列を見て迷う必要がなくなる
  • 「未解約」も OWL で書ける — 「解約日を 0 個持つ」という個数の条件だから (owl:maxCardinality)
  • ただし「直近 90 日」は OWL では書けない — 「今日」が無く、固定値との比較しか書けず、値と値も比べられないため。OWL のクラスは「いつ聞いても同じ集合」を表す道具で、毎日中身が変わるものは担当外
  • 時間に依存する条件は SPARQL / SHACL / バッチ再計算のどれかで扱う
  • xsd:decimal と xsd:double は互いに素。型を間違えると無言で 0 件になる
第 7 章

SPARQL — 書いた意味を引き出す

RDB に対する SQL が、RDF に対する SPARQL です。データを取り出すための問い合わせ言語で、これも W3C 標準です。ここまでで定義を書きました。この章でついに依頼に答えます。第 2 章の 84,500 円を、SPARQL で正しく導きます。

7.1 SPARQL は「穴あきトリプル」を並べるだけ

SPARQL の考え方は驚くほど単純です。トリプルの一部を変数（? 付き）にして並べる。合致するものを探してくる。それだけです。

リスト 7-1いちばん簡単な SPARQL

PREFIX ec: <http://example.com/ec#>

SELECT ?name WHERE {
  ?c a ec:顧客 ;          # 「顧客であるもの」を ?c とする
     ec:名前 ?name .        # その名前を ?name とする
}

結果HTTP で問い合わせたときに返ってくる JSON (SPARQL Results JSON)

{
  "head": { "vars": [ "name" ] },          # ← 変数名。? が取れている
  "results": {
    "bindings": [
      { "name": { "type": "literal", "value": "佐藤 花子" } },
      { "name": { "type": "literal", "value": "鈴木 一郎" } },
      { "name": { "type": "literal", "value": "田中 太郎" } },
      { "name": { "type": "literal", "value": "高橋 実" } },
      { "name": { "type": "literal", "value": "伊藤 桃子" } }
    ]
  }
}

形は単純です。head.vars に列名が並び、results.bindings に行が並びます。SQL の結果セットと同じ構造だと思って構いません。

ここで 2 つ気づいてほしいことがあります。1 つは head.vars が "name" になっていること。SELECT に書いた変数名が、そのまま列名になります (? は取れます)。

もう 1 つは、FROM も JOIN も書いていないこと。SQL なら必須のテーブル名を 1 つも指定していないのに、顧客 5 人が返っています。

7.2 なぜ JOIN を書かなくていいのか

「顧客の名前と、その注文の金額」を取ってみます。SQL と並べます。

リスト 7-2aSQL — JOIN 条件を書く

SELECT c.name, o.amount

第 8 章

SHACL — ルールを守らせる

ここまでは「読む」話でした。この章は「書き込みを止める」話です。そしてOWL と SHACL がなぜ両方存在するのかという、多くの解説が曖昧にする点を、具体データで決着させます。

8.1 守らせたいルール

表 1-3 を見てください。返金 R01 は 5,500 円で、対象の注文 O101 は 44,000 円です。当然、返金額が注文額を超えてはいけません。この制約を書きます。

リスト 8-1SHACL Shape — 返金の制約

@prefix sh: <http://www.w3.org/ns/shacl#> .

ec:返金Shape a sh:NodeShape ;
    sh:targetClass ec:返金 ;          # 検査対象 = 返金クラスの全インスタンス

    # ① 対象注文は必須
    sh:property [
        sh:path     ec:対象注文 ;
        sh:minCount 1 ;
        sh:message "返金には対象注文が必須です"@ja ] ;

    # ② 金額は 0 以上の decimal
    sh:property [
        sh:path          ec:金額 ;
        sh:datatype      xsd:decimal ;
        sh:minInclusive 0 ;
        sh:message      "返金額は 0 円以上でなければなりません"@ja ] ;

    # ③ 返金額は対象注文の金額を超えてはいけない
    #    ← 別ノード (注文) の値と比べるので sh:sparql を使う
    sh:sparql [
        sh:message  "返金額が対象注文の金額を超えています"@ja ;
        sh:prefixes ec: ;
        sh:select   """
            SELECT $this ?返金額 ?注文額 WHERE {
                $this ec:金額     ?返金額 ;
                      ec:対象注文 ?注文 .
                ?注文 ec:金額     ?注文額 .
                FILTER (?返金額 > ?注文額)
            }
        """ ] .

SHACL のルールは sh:NodeShape という単位で書きます。中身は「誰を 検査して、どのプロパティについて、何を要求し、違反したら何と言うか」の 4 つだけです。

書き方役割
a sh:NodeShape「これは検査ルールの束である」という宣言
sh:targetClass誰を検査するか。ここでは ec:返金 の全インスタンス
sh:property [ … ]1 つのプロパティについての検査。いくつでも並べられる (上では ① ②)
sh:pathその中でどのプロパティを見るか
sh:minCount / sh:maxCount個数の条件。minCount 1 は必須、maxCount 0 は「持ってはいけない」
sh:datatype / sh:minInclusive値の条件。型と下限
sh:message違反したときに返す文。これが機械可読な「理由」になる

sh:property を並べていくだけなので、ルールを足すのは行を足すことです。既存のルールを触る必要がありません。

8.2 Agent が暴走したときに何が起きるか

ここで AI エージェントが「O101 に 50,000 円返金する」という処理をしようとしたとします。O101 は 44,000 円の注文です。

図 8-1SHACL の門が Agent を止める

SHACL の価値は「止めること」より 「なぜ止めたかを機械可読で返すこと」

SQL の CHECK 制約では届かない

CHECK は同じ行の中の列比較しかできません。「返金額 ≤ 注文額」は refunds 表から orders 表を参照するので、CHECK では書けません。
結果、アプリ層で実装することになり、API・バッチ・管理画面・Agent の 4 経路で同じチェックを重複実装することになります。どこかで必ず漏れます。SHACL なら宣言 1 箇所で全経路に効きます。

第 9 章

「推論」という言葉は魔法のように聞こえますが、実際にやっているのは機械的な計算です。この章で、5 人のデータに対して推論器が何を出力するかを 1 件ずつ追います。

9.1 推論器とは何をする道具か

定義 — 推論器 (Reasoner)

TBox (定義) と ABox (データ) を受け取り、論理的に導ける新しい ABox を出力するプログラム。

代表的な実装が HermiT (Oxford 大学 / Java) です。オントロジー編集ツール Protégé に同梱されており、業界の標準的な選択肢になっています。他に Pellet・ELK・RDFox があります。

推論器は 3 段すべてを導きます。しかし ec:C002 a ec:顧客 はリスト 9-1 の ABox に元から書いてあるので、推論結果として新しく増えるトリプルは 1 本だけです。

推論器の出力を「増えた件数」で見ていると、この違いで混乱します。推論器が答えているのは「増えたか」ではなく「その型が成り立つか」です。第 12 章で COA の挙動を読むときも、この区別が効いてきます。

これが「上位クラスに 1 度書けば下位すべてに効く」の正体です。

寄り道 — 医療の定番例で、効き方を見る

この仕組みの価値が一番はっきり出る例を挟みます。薬の禁忌です。NSAIDs (非ステロイド性抗炎症薬) は妊娠後期に禁忌とされます。アスピリン・イブプロフェン・ナプロキセンは、すべて NSAIDs の一種です。

# 階層を宣言する
:Aspirin   rdfs:subClassOf :NSAIDs .
:Ibuprofen rdfs:subClassOf :NSAIDs .
:Naproxen  rdfs:subClassOf :NSAIDs .

# 禁忌は「上位クラスに 1 度だけ」書く
:NSAIDs rdfs:subClassOf [ a owl:Restriction ;
    owl:onProperty :禁忌 ; owl:someValuesFrom :妊娠 ] .

これだけで、下位すべてに効きます。図で追ってください。

図 9-1上位に 1 度書けば、下位すべてに効く — 医療の定番例

緑 = 人が書いた階層／赤 = 推論器が導いた結論。禁忌は 1 箇所にしかないのに、下位すべてに効く

RDB でこれをやると、薬 × 状態の禁忌マトリクスを作ることになります。薬が 1 つ増えるたびに、状態の数だけ行を人手で足す。実務では万件規模です。そして怖いのは、抜けてもエラーが出ないことです。「ナプロキセン × 小児」が 1 行抜けていても、システムは何も言いません。禁忌チェックが静かに通ってしまいます。第 2 章の 89,000 円と同じ形 — もっともらしく動くが間違っている状態です。

オントロジー側は、そもそも組合せを持ちません。「NSAIDs は妊娠中禁忌」という意味を 1 箇所に置き、あとは階層が配る。新薬が承認されても、書くのは rdfs:subClassOf :NSAIDs の 1 行だけです。

走る例に戻ります。ec:優良顧客 に何かルールを足せば、その下位クラス (たとえば ec:VIP対応必須) にも自動で効きます。仕組みは NSAIDs とまったく同じです。

9.5 推論器が「やらないこと」

期待しすぎないために、限界を明示します。

やらないこと理由
「無いこと」から結論を出す開世界仮説。佐藤さんに解約日が無くても「解約していない」と結論しない (第 8 章)
時間を扱う「今日」が無い。「直近 90 日」は書けない (第 6 章)
集計するSUM や COUNT は論理の仕事ではない。集計は SPARQL の役割
元データを書き換える推論は足すだけ。元の ec:会員ランク は書き換わらない
矛盾を自動で直す矛盾は検出して報告するだけ (「Inconsistency」と教えてくれる)
実運用での落とし穴 — 型が違うと無言で 0 件

第 6 章の罠がここで実害になります。データ側が xsd:double、公理側が xsd:decimal だと、推論結果が 1 件も出ません。しかもエラーは出ません。

VKG = Virtual Knowledge Graph。「仮想的な知識グラフ」という意味です。オントロジー導入の最大の壁は「既存 DB を全部 RDF 化するコスト」でしたが、この章の技術がその壁を丸ごと回避します。

11.1 「対応表」を書くだけ

第 4 章では customers 表を手で Turtle に書き写しました。しかし実務でそれをやると、元の DB と Turtle の二重管理が始まります。

そこで R2RML (RDB to RDF Mapping Language / W3C 勧告) を使います。「この表のこの列は、オントロジーのこのプロパティに対応する」という対応表だけを書きます。

どの DB に繋ぐかは、R2RML には書きません。接続情報 (ホスト・ユーザー・パスワード) は別の設定として渡します。だから同じ対応表を、開発用 DB と本番用 DB に向け直せます。第 14 章のデモでは、この「接続先」に相当するのが COA の Data Source 登録です。

11.5 仮想化の代償 — 推論が回せなくなる

表の中で 1 行だけ、仮想化が負けている項目がありました。推論です。ここは軽く流せない場所なので、節を分けて見ます。

なぜ回せないのか

第 9 章で、推論器は「鈴木さんも優良顧客だ」と導きました。あのとき推論器がやったことを分解すると、こうです。

  1. TBox から定義を読む — 「優良顧客とは、累計購入額が 50,000 円以上の顧客である」
  2. ABox から実データを読む — 「C002 鈴木一郎の累計購入額は 55,000 円」
  3. 2 つを突き合わせて、書いてない事実を足す — 「C002 は優良顧客である」

問題は 2 番目です。推論器は、定義と実データが同じ場所に揃って初めて動きます。そして VKG は、その実データをあえて手元に置かない設計でした。

図 11-5推論器が動く条件 — マテリアライズでは揃い、仮想化では揃わない

推論器は定義と実データが同じ場所に揃って初めて動く。VKG は実データをあえて手元に置かない設計なので、ここが構造的にぶつかる

「ならクエリのたびに元 DB から引けばいい」と思えますが、そうはいきません。推論は全件を見ないと成立しない処理です。「50,000 円以上の人」を漏れなく挙げるには、顧客表を最後の 1 行まで読む必要があります。図 11-4 で見たとおり ABox は数億行あるので、質問 1 回ごとに数億行を SELECT して RDF に変換することになります。秒で返る処理ではありません。

だから実際の製品は、次の 3 つのどれかを選びます。「推論をクエリ時に回さない」という点ではどれも同じで、違うのは代わりに何を置くかです。

① 推論を諦める — 条件を SPARQL 側に書く

OWL の定義（リスト 6-2）は書いたまま、推論器を走らせません。絞り込みは SPARQL の FILTER でやります。第 7 章のリスト 7-3 がまさにこれで、実は本書はここまで、ずっとこの方式で動いてきました。

図 11-6① 推論を諦める — 同じ数字が 2 箇所に分かれる

今すぐ動くのが最大の利点。ただし §2.4 で嫌った「変更が掛け算で効く」が、小さい規模で戻ってくる

代償は同じ条件が 2 箇所に書かれることです。基準を 50,000 円から 40,000 円に変えるとき、OWL の定義と SPARQL の両方を直します。片方だけ直しても、誰もエラーを出しません。

それでも OWL 側を書く価値は残ります。人間と LLM が読む「正解の置き場所」になるからです。第 5 章で見たとおり、rdfs:label と rdfs:comment と定義が揃っていれば、LLM は「優良顧客」という言葉から FILTER(?t >= 50000) を自分で書けます。推論器が使わないだけで、無駄になるわけではありません。

② バッチで回す — 夜間に型付与だけを書き戻す

夜間に 1 回、ABox を全件読んで推論を回します。ただし書き戻すのは推論の結果だけです。ec:C002 a ec:優良顧客 のような型付与のトリプルが数千行できるので、それだけを Triple Store に入れます。実データそのものは動かしません。翌日のクエリは、その型付与を読むだけなので速い。

図 11-7② バッチで回す — 速さを買って、鮮度を売る

日次のレポート用途なら十分。しかし「今この人は優良顧客か」を聞かれる用途には向かない

代償は鮮度です。§11.4 の表で仮想化の利点だった「常に最新が見える」を、推論の結果については手放すことになります。夜間バッチと聞くとマテリアライズに近づいたように見えますが、違います。移すのは推論結果の数千行だけで、数億行の実データは元 DB に残ったままです。図 11-4 の非対称は保たれています。

③ 定義の検査にだけ使う — ABox の推論は諦め、TBox だけを検査する

3 つめは考え方が違います。§4.3 の言葉で言うと、こうです。ABox（実データ）への推論は諦める。代わりに TBox（定義）そのものに推論器を向けて、定義同士が矛盾していないかを検査する。推論器に渡すのは TBox だけで、実データは 1 行も渡しません。

具体例を出します。オントロジーは 1 人が一気に書き上げるものではなく、何人かが何ヶ月かかけて足していきます。あるとき、こうなっていたとします。

★ 最重要図 11-8誰も入れないクラスを、データを 1 行も読まずに構築時に見つける

データの推論を完全に諦める代わりに、定義そのものの矛盾を無料で拾える。VKG と両立する唯一の使い方

言葉で辿ります。A さんは「優良顧客は個人顧客の一種だ」と書きました。B さんは「優良顧客は法人顧客の一種だ」と書きました。どちらも単体なら、もっともらしい定義です。ところがオントロジーには前から「個人顧客と法人顧客は重ならない」という宣言が入っていました。

矛盾を作っているのは、この 3 番目です。rdfs:subClassOf が 2 本あるだけなら、推論器は何も言いません。OWL では、クラス名が違うだけで「重ならない」ことにはならないからです。1 つのものが複数のクラスに属するのは、むしろ普通のことです（第 5 章の ec:優良顧客 も ec:顧客 でもありました）。owl:disjointWith で「この 2 つは重ならない」と明示的に宣言してあって初めて、両方の一種であることが不可能になります。

この 3 つを全部守ろうとすると、優良顧客であるためには個人顧客であり、同時に法人顧客でもある必要があります。しかしその 2 つは重ならないと宣言済みです。つまり ec:優良顧客 は、条件を満たす顧客が 1 人も存在しないクラスになってしまいました。

推論器はこれを構築時に「このクラスは充足不能である」と報告します。定義の矛盾は、データを見なくても定義だけから導けるからです。第 9 章で「書いてない事実を導く」と説明した力が、そのまま「書いてはいけない組み合わせを見つける」力にもなっている、ということです。

代償はABox の推論を全部諦めることです。鈴木さんに ec:優良顧客 は付きません。得られるのは「TBox そのものが壊れていないこと」の保証だけです。

TBox の検査で拾えないもの — ここが SHACL との境界

捕まえられるのは定義同士の矛盾だけです。「データが定義に違反している」ことは捕まえられません。たとえば ec:C001 が個人顧客であり法人顧客でもあるとABox に書かれていても、TBox しか渡されていない推論器は気づきません。

そちらは SHACL の担当です (第 8 章)。第 8 章で「OWL は型を定義する道具、SHACL は検査する道具」と分けたのと同じ線が、ここでも引かれています。③ が守るのは定義の側、SHACL が守るのはデータの側です。

3 つを並べる

選択肢推論はいつ走るか得られるもの手放すもの
① 諦める走らない今すぐ動く。常に最新。実装が一番軽い同じ条件が OWL と SPARQL の 2 箇所に書かれる
② バッチ夜間に 1 回推論の結果が使える。クエリは読むだけで速い鮮度。次のバッチまで昨夜の答えを返し続ける
③ TBox の検査構築時に 1 回
（渡すのは TBox だけ）		定義同士の矛盾を公開前に止められる。コストはほぼゼロABox の推論を全部。鈴木さんに優良顧客は付かない
COA が選んでいるのは ③ + ①

第 12 章で見る COA は、推論器を構築フェーズで TBox の整合性を検査するためにだけ使い、クエリ時には走らせません（③）。そして実際の絞り込みは ① の形で行われます — 生成される SQL の中に total_purchase >= 50000 が書かれます。

だから第 6 章で見た「ルールでは 4 名、member_rank 列では 2 名」のズレは、検知はできるが、推論器が黙って直してくれることはないという状態になります。誰が直すかを決めるのは、人間の運用の側です。

第 11 章のまとめ

  • 外部キーがURI へのリンク (矢印) に変わる。JOIN が hop になる
  • Ontop が SPARQL を実行時に SQL へ翻訳する。データは 1 バイトも動かない
  • Triple Store に入るのは TBox (数千トリプル)。ABox は元 DB に残る (数億行でも可)
  • 規制でデータを移せない業界にとって、これが導入可否を決める
  • マテリアライズとの差は保管コストと管理の手間。マテリアライズは元の数倍に膨らみ、二重管理になる
  • ただし代償がある — ABox が手元に無いので推論が回せない。打ち手は 3 つで、① 諦めて FILTER に書く / ② 夜間バッチで型付与だけ書き戻す / ③ ABox は諦め TBox の検査だけに使う

第 12 章

COA は何を実装したのか

最後に実際の製品を見ます。AWS の COA (Context Ontology Accelerator) は、ここまでの道具のうち何を実装し、何を実装していないのか。公開ソースコードを読んで確認した内容です。

12.1 COA がやろうとしていること

COA の狙いは一言で言えます。「オントロジーを LLM のグラウンディング層として使う」。つまり、第 2 章の事故を防ぐために、LLM が SQL を書く前にオントロジーを読ませます。

12.2 2 つのフェーズに割れている

ここが最も重要な構造です。COA は「構築」と「クエリ」が完全に別のプロセスに分かれています。

図 12-1構築フェーズとクエリフェーズ — 推論器はどこに居るか

推論器と SHACL は「構築フェーズでオントロジー自身を検査する」ために使われている。クエリ結果の検査に使われるのは、赤い箱の機械的な検査 4 種だけ

12.3 この題材で考えると、どうなるか

第 6 章で書いた優良顧客ルールを COA に入れたとします。何が起きるでしょうか。

期待実際理由
ルールが矛盾していないか検査してくれるされる構築時に HermiT が整合性を検査し、矛盾があれば公開自体をブロックする
xsd:decimal / xsd:double の型ミスを教えてくれるされる専用の型トークン検証器がある。第 6 章の罠は構築時に検出される

LLM が正しい列名・JOIN 経路で SQL を書くなる抜粋をプロンプトに入れる仕組みが実装されている (次項)

第 2 章の事故が防げる理由が、ここにある

最後の Glossary の note を見てください。「直近 90 日以内に購入した、解約していない顧客」と書いてあります。

第 2 章の新人は、この情報が無かったので「30 日くらいかな」と推測しました。この 1 行がプロンプトに入っていれば、推測する必要がありません。

同様に allowed values: ["VIP", "Regular"] があれば、"vip" と小文字で書いて 0 件になる事故も防げます。Join paths があれば JOIN 条件を当てる必要がありません。

ただし — この note を書くのは人間です。空欄なら、空欄のまま LLM に渡ります。

12.5 生成後の検査

LLM が SPARQL や SQL を出した後、COA は 4 つの門で機械的に検査します。

門やること落ちたらどうなるか
① 構文検証SPARQL としてパースできるか (rdflib)次の段にフォールバック
② URI 実在確認生成された URI が Neptune に実在するかを問い合わせる同上。幻覚 URI を捕まえる主要な仕掛け
③ 認可この人がこの名前空間を検索してよいか終端 (403)
④ SQL FirewallSELECT 以外を拒否 / 危険関数を遮断 / 表・列の許可リスト終端。解析できなければ拒否 (fail-closed)
正しい理解の仕方

COA の制御は「LLM を決定論に置き換える」ものではありません。実際にやっているのは 3 つです。

① 見せる範囲を絞る — 答えられないクラスはプロンプトに載せない
② 材料を正確に渡す — 実際の値・JOIN 経路・用語の定義
③ 出てきたものを機械的に検査する — 構文・URI 実在・認可・SQL 安全性

クエリ生成そのものは最後まで確率的です。変わるのは 外し方が予測可能になり、検証できるようになることです。

第 12 章のまとめ
  • COA は構築フェーズとクエリフェーズが完全に分離している
  • HermiT と SHACL は構築時にのみ動く — オントロジー自身の検査のため。クエリ時には走らない
  • プロンプトには Turtle ではなく整形した抜粋が入る (値・JOIN 経路・用語集)
  • 用語集の note が第 2 章の事故を防ぐ鍵。ただし書くのは人間
  • 生成後に 4 つの門で機械的に検査する

13.2 最初にやると効くこと

推論器を動かす前に、元が取れる作業

第 6 章で見た 「ルールでは 4 名、member_rank 列では 2 名」というズレの検出を思い出してください。これは推論器も SHACL も不要です。ルールを 1 箇所に書いて、現状と突き合わせるだけで見えます。

実務での最初の一歩としては、これで十分な価値があります。

  1. 自部門で定義が割れている用語を 3 つ書き出す (「アクティブ」「売上」「解約」あたりで必ず見つかります)
  2. それを Turtle で 10 行書く。rdfs:label と rdfs:comment だけでも構いません
  3. 現在のデータと突き合わせて、ズレている件数を数える

ズレの件数が出れば、それが投資判断の材料になります。

13.3 この本の結論

結論

オントロジーは「答えを出す魔法」ではありません。
「組織のルールを一箇所に置く場所」です。

推論器や検証器は常時オンである必要はありません。定義さえ 1 箇所に集まっていれば、効かせる実装は後から接続できます。バッチで推論を回すのでもいい。SPARQL の FILTER で書くのでもいい。SHACL を書き込み経路に置くのでもいい。

逆に言えば、定義が散らばっている限り、どんな道具を入れても解決しません。同じ条件が 3 つの Lambda と 2 つの API と 4 つのバッチにコピーされている状態を、まず 1 個の定義に集約すること。それがこの本で学んだ全部の道具の、共通の前提です。

第 13 章のまとめ
  • 意味に起因する問題 (シノニム・JOIN・集計定義・値の揺れ・型・階層・制約) は解ける
  • 時間依存・「無いこと」・方言・性能はオントロジーの担当外
  • 最大のコストは「定義を誰が書くか」。ここは技術では解けない
  • 最初の一歩は「割れている用語を 3 つ書き出し、ズレを数える」

デモ ① AWS COA — 定義を 1 箇所に置くと、LLM の出力が変わる

14.1 このデモが証明すること

14.3 ⑥ が実は一番大事

⑤ は派手ですが、確率的です。同じ質問を 3 回すれば 3 回同じ結果になるとは限りません。⑥ は決定論的で、しかも推論器も検証器も要りません。ルールを 1 箇所に書いて現状のデータと突き合わせるだけです。

デモで一番効くのはこの 1 行

「ルールでは 4 名、member_rank 列では 2 名。差の 2 名 — 鈴木さんと田中さんは、VIP 対応すべきなのに Regular のままです」

これは推論器を立てる前に、Turtle を 10 行書くだけで出てきます。第 13 章 §13.2 で「最初にやると効くこと」として挙げたのがこれです。投資判断の材料が、投資する前に手に入るという構造になっています。

なぜ「差の 2 名」と言えるのか — 引き算が成り立つ条件

4 − 2 = 2 という計算が意味を持つのは、VIP の 2 名 (C001 佐藤・C005 伊藤) がどちらもルールを満たしているときだけです。もし「VIP なのに累計 50,000 円未満」の人が混ざっていると、件数の引き算は昇格対象者の数になりません。

実務のデータでは、これが普通に混ざっています。だから件数を引き算する前に、必ずどちらの集合に誰が入っているかを並べて確認すること。第 6 章の表 (誰が一致し、誰がズレているか) を作るのが先で、件数は後です。

第 15 章

デモ ② Palantir Foundry — オントロジーが「行動」まで持つとどうなるか

2 つめは Palantir Foundry です。COA との違いは技術の優劣ではありません。オントロジーという言葉に何を含めているかが違います。Palantir の公式教材の定義を読むと、その違いが 1 行で分かります。

15.1 Palantir の定義 — data, logic, and actions

Palantir 公式教材の記述

15.2 デモが扱う業務 — 臨床試験の患者リクルート

公式教材が使う業務はこれです。手順は 3 段階に符号化されています。

この形に見覚えがあるはずです。調達業務の「見積 → 交渉 → 説明 → 申請 → 決裁」と同じ構造です。判断の連鎖があり、途中に人間の承認点があり、各段が前段の結果に依存する。Palantir が狙っているのはこの領域です。

15.3 教材の 3 部構成が、そのまま設計思想になっている

コースは Agent を「作る → 評価する → 自動化する」の 3 部でできています。この 3 部構成自体が、COA との最大の違いを示しています。

コース最後の「患者を 1 人追加すると、Agent が自動で適格性を判定する」だけで十分です。ここに Palantir の思想が全部入っています。

人間はデータを 1 件足しただけです。誰も Agent を呼んでいません。オントロジーに患者オブジェクトが増えたというイベントが、Automation を起動し、Agent が判定し、結果がまたオントロジーに書き戻される。オントロジーが「業務が流れる場所」になっています。

15.4 では、どちらを選ぶのか

「どちらが優れているか」という問いは噛み合いません。解こうとしている問題が違います。

判断の分かれ目

AWS COA が向く場面 — 既存の RDB を動かせない。データを外に出せない。まず「意味のズレ」を可視化したい。W3C 標準に載せて資産を長く持ちたい。読む側の統制が課題のとき。

Palantir が向く場面 — 業務プロセスそのものを Agent に流したい。書き込みと承認と自動実行まで含めて 1 つの上に載せたい。評価の仕組みも製品として欲しい。業務を動かす側が課題のとき。

そして予算の桁が違います。この本で学んだ W3C の道具は、Turtle を 10 行書くところから始められます (第 13 章 §13.2)。Palantir は業務 OS として導入する規模の話になります。

Palantir を「オントロジーの正解」と紹介しないこと

Palantir は自社の中核概念を Ontology と呼びますが、W3C の RDF / OWL / SPARQL は使っていません。独自のオブジェクトモデルです。したがって「Palantir がやっているからこれがオントロジーだ」とは言えません。

逆に「W3C 標準じゃないから本物のオントロジーではない」とも言えません。次の章で見るように、RDF を使っていなくてもオントロジーとして機能するものはあります。大事なのは記法ではなく、定義が 1 箇所にあって機械が計算に使えるかどうかです。

  • Palantir はオントロジーをデータ・ロジック・アクションの統合と定義する。COA にはアクションが無い

第 16 章

デモ ③ Minecraft — 自律ループの最小模型

最後は Minecraft です。本番業務でやると危ない「Agent が自分で判断して世界を書き換える」を、構造を保ったまま安全に見せられます。ただし最初に 1 つ訂正しておくべきことがあります。

16.1 訂正 — このデモは RDF を使っていない

実装を読んで確認した事実

この Minecraft デモは、これまでの資料で「Turtle / OWL / SPARQL をフル活用」「Neptune + HermiT + Ontop VKG」と説明されていました。実装を読むと、そうではありません。

.ttl ファイルは 1 つも存在せず、実装コードに rdflib・SPARQL・Neptune・HermiT はいずれも登場しません。オントロジーの実体は 04_ontology_agent/ontology.py の中の NetworkX の有向グラフです。LLM も Bedrock ではなく、ローカルの Ollama で動く qwen2.5:7b です。

勉強会でこの資料を見せる前に、必ずここを直してください。コードを見せてくれと言われた瞬間に崩れます。

そして — これは弱点ではありません。むしろこの章で一番教育的な事実です。RDF を使っていないのに、この実装はオントロジーとして機能しています。それはなぜかを見ていきます。

16.2 何をオントロジーと呼んでいるのか

実体は「作りたいもの → その材料 / 必要な道具」を辺で結んだグラフです。第 3 章で見たトリプルの構造と、実は同じことをしています。

リスト 16-1ontology.py — グラフの定義 (抜粋)

# 石のツルハシ = 丸石 x3 + 棒 x2
g.add_edge("stone_pickaxe", "cobblestone", relation="material", qty=3)
g.add_edge("stone_pickaxe", "stick",       relation="material", qty=2)

# 丸石は木のツルハシ以上で採れる
g.add_edge("cobblestone", "wooden_pickaxe", relation="tool_needed")
g.add_edge("cobblestone", "stone_block",    relation="obtained_from")

(stone_pickaxe, material, cobblestone) — 主語・述語・目的語です。第 3 章で「トリプルは世界を 3 語で書く」と説明したのと、形は同じです。

ただし違うところが 1 つあります。意味を持っている場所です。

この Minecraft のグラフRDF / OWL

(何と何が繋がるか)		グラフが持つオントロジーが持つ
意味
(そこから何が導けるか)		読む側の Python 関数が持つオントロジー自身が持つ

relation="material" が何を意味するかは、それを読む to_prompt_text() と sort_actions() の中にしか書かれていません。OWL は含意が仕様として定義されているので、どの推論器で読んでも同じ結論が出ます。ここが「書き方の違い」ではなく「種類の違い」です。

そしてこのグラフは、そのまま文字列に変換されて LLM のプロンプトに入ります。

COA の format_for_prompt() がやっていることと設計が同じです。グラフを持っておいて、LLM に渡すときは整形したテキストにする。Turtle をそのまま LLM に渡すのではないという点まで一致しています。

ここから言えることは、「構造があれば機械は計算に使える」ということです。第 2 章 §2.4 で「プロンプトに文章で書く方法は行き止まり」と書いたのは、文章が構造を持たないからでした。その意味では、Python のグラフでも目的は果たせます。

ただし「だから RDF は要らない」とは言えません。次の項で、このグラフに何が足りないかを実測で見ます。

16.3 何が足りないのか — 実測で確かめる

このグラフを「オントロジーだ」と言うとき、何を諦めているのかをはっきりさせておきます。抽象論ではなく、実際にコードを動かして確かめます。

グラフのノードには kind という属性が付いています。craftable (作れる) / harvestable (採れる) / tool (道具) / natural_block (自然物)。これは第 4 章の a (rdf:type) に相当します。ではこのグラフに「道具を全部挙げて」と聞いてみます。

リスト 16-3ontology.py を実行して型を数える

>>> g = build_ontology()
>>> [n for n, d in g.nodes(data=True) if d.get("kind") == "tool"]
['hand']                      ← 素手だけ

>>> g.nodes["wooden_pickaxe"]["kind"]
'craftable'                  ← 道具になっていない

>>> g.get_edge_data("cobblestone", "wooden_pickaxe")
{'relation': 'tool_needed'}   ← なのに「必要な道具」として使われている

静かなデータ欠落が、実際に起きている

木のツルハシと石のツルハシは、道具として記録されていません。コードには道具として登録するループがちゃんと書かれているのに、です。原因は NetworkX のノード属性が単一値だからです。wooden_pickaxe には先に craftable が入り、道具のループはそれを見て飛ばします。stone_block は逆にガードが無く、harvestable が natural_block に上書きされて消えています。

RDF なら、型を並べて書くだけで済みます。1 つのものが複数の型を持つことに、何の細工も要りません。

:wooden_pickaxe a :Craftable, :Tool .

そして、もう 1 つ深刻なことが起きています。tool_needed という関係の目的語なのに、その相手が道具として型付けされていない。これは食い違いですが、誰も検出しません。このグラフには「矛盾」という概念自体が無いからです。第 8 章の SHACL があれば sh:class 1 行で捕まります。

16.4 では、これはオントロジーなのか

整理します。古典的な定義は「形式的で・明示的な・共有された概念化の仕様」です。3 つのうち 2 つは満たしています。

条件満たすか中身
明示的満たす依存関係が人の頭ではなくファイルに書かれている
共有された満たすLLM と Python が同じ 1 つの構造を読んでいる
形式的弱い含意を決めるのが読む側のプログラム。仕様として定義されていない

持っているものと、諦めているものを並べます。

持っている諦めている
名前付き・型付きの関係 (material / tool_needed / obtained_from)。ここが「線で繋がった図」との決定的な差クラスとインスタンスの区別 (第 4 章 §4.3 の TBox / ABox)
関係に属性が付く (qty=3)包摂階層。だから「上位に 1 度書けば下位すべてに効く」(第 9 章 §9.4) が原理的にできない

正確な言い方

「オントロジーじゃない」と切り捨てるのも、「これもオントロジーだから W3C 標準は要らない」と言うのも、どちらも不正確です。このデモがやりたいこと (機械が LLM を矯正する) には、これで足りています。足りなくなるのは、型を複数持たせたいとき・階層を効かせたいとき・矛盾を検出したいとき・他システムと統合したいときです。上の実測は、その 1 つ目にすでにぶつかっていることを示しています。

16.5 「それ、RAG でよくないですか」に答える

この質問は必ず出ます。「クラフトの依存関係も知識なんだから、社内 Wiki に書いて RAG で LLM に読ませればいいのでは」。もっともな指摘です。だから実際に 3 通り作って比べてあります。同じ 7B のローカル LLM・同じタスク・同じアクション集で回した結果です。

RAG の限界と、オントロジーの真価

RAG は「関連情報を LLM に届ける」ことしかできません。LLM が読み違えたとき — 順序を間違える、前提を飛ばす、同じ手順を 2 回書く — それを外から検証する仕組みが無いのです。

オントロジーの真価は、構造化されているので プログラムが LLM を検証し、矯正できることにあります。「LLM に情報を渡す」だけでなく「LLM の間違いを直す」まで含めて設計できる。第 0 章の図 0-2 で言えば、機械の担当が仕事をできるようになる、ということです。

結論は RAG はオントロジーの代替ではなく補完です。参考知識の供給は RAG、実行構造の保証はオントロジー。目的で使い分けます。

このデモの核心です。ACTION_DEPS という辞書に「どのアクションがどのアクションの後でなければならないか」を書いておき、Python 側でトポロジカルソートします。

リスト 16-4実測ログ — 「石のツルハシを作って」

▶ タスク: 石のツルハシを作って

      1. mine_stone
      2. craft_stone_pickaxe
      3. mine_stone          ← 同じ手順を 2 回出している

これが第 0 章の図 0-2 の実物

LLM の担当は「何をすべきか、だいたいの見当をつける」。機械の担当は「順序を保証し、抜けを補い、実行する」。どちらか一方では動きません。

業務システムに置き換えると、LLM が出した処理計画を、依存関係の定義に照らして並べ替え・不足分を補完してから実行する、という構造になります。第 14 章の COA で「生成後に 4 つの門で検査する」と言ったのと、同じ発想の別の実装です。

実装中に踏んだ罠が、そのまま業務システムの教訓になっています。

第 13 章 §13.1 の表の最後に、この行が入っています。「その操作が、今この瞬間に実行可能か」。オントロジーは定義と関係の世界にいるので、在庫があるか・権限が生きているか・対象レコードが実在するかは知りません。実行前の存在確認は、必ず別に用意する必要があります。

第 16 章のまとめ
  • このデモは RDF を使っていない。実体は NetworkX の有向グラフと、ローカルの 7B モデル。資料の記述を先に直すこと
  • それでもオントロジーとして機能する。ただし正確には軽量オントロジー — 明示的・共有されてはいるが、形式的ではない
  • 違いは記法ではなく意味を持つ場所。このグラフの意味は読む側の Python が持っているので、プログラムを変えると意味が変わる
